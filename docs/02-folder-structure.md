# 2. What Will the Folder Structure Be Like?

## The table

| Part | Now (Start) folder structure | Future (Scale) folder structure | Notes / Reason |
|---|---|---|---|
| **Backend** | One app, `src/platform/` (kernel) + `src/products/{key}/` (one folder per product), `src/shared/` (infra adapters). | Each extracted product becomes `services/{key}/` with the *same internal layout*; the kernel becomes `packages/platform-kernel/` consumed by all services. | A product folder is already a complete, self-contained unit. Extraction is `git mv`, not reorganisation. |
| **Admin** | `apps/admin/` — separate Next.js app, feature-based, sharing `@helix/ui` and `@helix/sdk`. | Same shape; splits into `apps/admin-ops/` and `apps/admin-support/` when the audiences diverge. | Separate deployable from day one because of blast radius; separate *repos* never, because sharing the design system matters more. |
| **Frontend** | `apps/web/` — platform shell in `src/app/`, product UIs in `src/app/apps/{key}/`, cross-cutting logic in `src/features/`. | Each product UI becomes `apps/web-{key}/` exposing a federated remote; `apps/web-shell/` hosts them. | Product UIs are already isolated by route folder, so the micro-frontend split is a move plus a Module Federation config. |

## Future (Scale) — the same tree, redistributed

```
helix-platform/
├── services/                    # products that met an extraction trigger
│   ├── calendar/                #   ← was apps/api/src/products/calendar/, unchanged inside
│   │   ├── src/{api,domain,infra}/
│   │   └── prisma/schema.prisma #   ← was the `calendar` schema, now its own database
│   ├── meet/
│   ├── meet-sfu/                #   media plane (was separate from day one)
│   ├── search/                  #   OpenSearch indexer + query service
│   └── notifications/
│
├── apps/
│   ├── api/                     # still hosts the long tail of low-traffic products
│   ├── gateway/                 # Envoy/Kong config, route table, edge policy
│   ├── web-shell/               # micro-frontend host
│   ├── web-calendar/            # federated remote, deployed independently
│   ├── web-meet/
│   └── admin-ops/  admin-support/
│
├── packages/
│   ├── platform-kernel/         # ← was apps/api/src/platform/, now a library
│   ├── core/                    # unchanged: the contract everything still obeys
│   └── ui/  sdk/  observability/
│
└── infra/
    ├── k8s/cells/{us-east,us-west,eu-central,ap-south}/
    └── terraform/modules/cell/  # a cell is a reproducible unit, not a snowflake
```

**The point of showing both trees is that they are the same tree.** Nothing is
renamed, re-layered or rewritten — folders move up a level and gain a
`package.json`. That is only true because the boundaries were real from the start.

## How the structure demonstrates each requirement

| Requirement | Where it lives | The decision behind it |
|---|---|---|
| **Separation of concerns** | `platform/` (cross-cutting) vs `products/` (domain) vs `shared/` (infrastructure) | Three directories, three reasons to change. A product folder contains no infrastructure and no security code. |
| **Modular architecture** | `products/{key}/` is self-contained; deleting the folder removes the product | Verified by the extraction runbook: a product folder has no inbound imports. |
| **Reusable components** | `packages/ui` (design system), `packages/sdk` (API client), `packages/core` (contracts) | Shared *code* lives in packages; shared *behaviour* lives in the kernel. Confusing the two is how platforms end up with 100 copies of a permission check. |
| **Feature-based organisation** | Both backend (`products/{key}/`) and frontend (`app/apps/{key}/`, `features/`) group by feature, never by technical layer | A layer-based tree (`controllers/`, `services/`, `models/`) makes every product change touch every directory, and makes extraction impossible. |
| **Shared libraries** | `packages/*` — versioned by the workspace, built by Turborepo, no publish step | One `pnpm build` builds the graph in dependency order. |
| **Authentication & authorisation** | `platform/auth/`, `platform/rbac/`, `shared/http/guards/` — registered **globally** in `app.module.ts` | Protected by default, opt out with `@Public()`. Forgetting a decorator locks a route down; it never opens one up. |
| **API management** | `/v1/{product}/…` versioned per product; OpenAPI generated at `/docs`; `packages/sdk` generated from it | Versions are per product so a Calendar v2 does not force 99 other products to move. |
| **Configuration management** | `shared/config/configuration.ts` — zod-validated once at boot; `.env.example` documents every variable | A missing variable crashes the process at start, not a request at 3am. |
| **Testing** | Unit tests beside source; contract tests per product; `packages/core` tests the registry rules; `prisma/sql/verify_tenant_isolation.sql` proves isolation | The isolation test is SQL, not a mock, because the control being tested is a database policy. |
| **Documentation** | `docs/` (answers), `docs/adr/` (why), `products/{key}/README.md` (boundaries + extraction checklist), OpenAPI (API) | Each product carries its own extraction runbook, so the knowledge does not live in one architect's head. |
| **Future expansion** | `tools/generators/product/` + the manifest contract | Adding product #101 is a command. The structure does not change when the product count changes — that is the whole test of a scalable structure. |
